## 2. 敌人 AI 与群体 AI

### 群体 AI：明确有票据与角色系统，但还没有完整调度策略

本地 PDB 中存在 `FAIAttackTicketManager`、`FAIAttackHandler`、`ESCAICombatRoles`，本地资产中实际读到 50 个攻击票据资产。

票据配置明确分开：数量、按难度的数量、冷却组、角色掩码、同步出手冷却偏移、直接对手死亡后的强制冷却、fallback 等。

例如 `DB/AI/Tickets/Attack/AttackTicket_DirectOpponnent` 明确保存 `m_iCount=1`、按难度数量 `[1,1,1]`、`m_bUsePerDifficultyCounters=true`。它有 4 个基础冷却槽位，也有 3 组按难度的配置，每组包含 4 个冷却槽位。当前保留原始数组索引，不把四个槽位擅自命名成难度，也不将这个单一票据的 count=1 推广为“全场最多一个敌人攻击”。

本地角色枚举确认 `DirectOpponent=1`、`IndirectOpponent=2`、`NonOpponent=3`。如何选人、距离/视线权重、是否可抢占、何时释放、与全部票据的总并发关系，仍需沿实现和实际引用核对。

### 已确认的状态绑定 1：倒地/起身进入攻击票据情境

本地 `EFightingState::KnockedDown=3`；`EAIAttackTicketJokerSituation::TargetKnockedDown=11`、`TargetGettingUp=12`。

对匹配 PDB 中的真实函数范围反汇编，`FAIAttackTicketManager::OnDefenderFightingStateChanged`（RVA `0x185c690`，23 字节）会：

1. 比较传入的 state 是否为 3；其他值直接返回。
2. 根据传入布尔标记选择情境 11 或 12。
3. 调用 `ActivateJokerSituation`，第三个参数置 false。

这证明了“倒地状态变化回调 → 票据情境”的实际代码映射。布尔标记的完整调用约定、激活情境后具体开放/禁止哪些票据、冷却或配额如何变化，还没有完整恢复。因此不能直接说它一定会让敌人抢攻或停止攻击。

### 已确认的状态绑定 2：硬直存在有条件的连招结束路径

`UAIFightingComponent::OnIsStunChanged` 调用 `UHitComponent::IsStun`，并把布尔值传给 `FAIAttackHandler::OnIsStunChanged`。

后者在 false 时直接返回；为 true 时读取黑板 enum，在读值非 0 的路径调用 `EndCombo`，结束原因传入 `0x0A`。本轮没有确认该 reason 的枚举名字，也没有把所有黑板值映射为业务状态。

这是硬直与 AI 连招生命周期之间的实际关联，不等于“任何受击都必定打断”或“全部硬直都会释放攻击票据”。

### 个体防御：攻击记忆、状态标签、Structure 与难度测试

`Grunt_Base_ContextualDefense` 的 63 个 export 已读出，包括：11 个攻击记忆测试、9 个攻击属性测试、18 个测试序列，以及招架、闪避、闪身、防御等节点。另保存了 Advanced 版本，合计 129 个对象供对照。

本地例子：

- `AttackMemoryInfluenceTest_0` 对应 tag `Attack.Specific.BackFrontPush`，保存 `m_fMemoryLimit=3`、`m_uiHitsCount=1`、`m_HitTypes=2`。
- 同资产还存在 memory limit 2/5/10 等值和命中次数不同的测试。
- `DefenseInfluenceNodeParryDeflect_0` 的成功标签配置包含 `AI.Grunt.FirstParry`，并引用 `BP_AiLaunchCounterCombo_Parry` 动作实例。
- 存在 `StructureInfluenceTest`（序列化 ValueMax≈0.4）和 DifficultyInfluenceTest。

以上证明存在相关配置和引用。记忆是否按时间/招式/结果刷新、各 hit mask 的含义、是否计入同类招式、是否产生可观察的自适应防御，仍需函数逻辑验证。不能仅凭 `MemoryLimit=3` 就称作“记住最近3秒”，也不能凭 0.4 就断言判定是“当前架势低于40%”。

## 3. 冲击、削韧和硬直：必须分开看

本地 HitImpact 数据把下列量分开保存：生命伤害、Structure 伤害、SuperDizzy 伤害、受击硬直帧、击退距离、停顿帧。命中、防御、Deflect 各有独立分支。PDB 的 `FAppliedHitImpact` 也确认这些量各有字段，并非同一数值。

导出共 855 个 HitBox 数据行，每行按三个结果分列，共 2,565 条记录。每个数值相邻的 `m_bUse...` 开关保留在表里；false 不等于实战最终值为0，可能改用默认值或其他来源。

以 `DB/AI/Archetypes/Grunt/Attacks/Grunt_HitBoxData` 的 `Jab_HB01` 为例，仅表示本地存储值：

| 字段 | 命中 m_OnHitImpact | 防御 m_OnGuardImpact |
|---|---:|---:|
| Damage | 15（启用） | 0（启用） |
| StructureDamage | 18（启用） | 15（启用） |
| NbFrameStuned | 15（启用） | 15（启用） |
| FreezeFrames | 4（启用） | 4（启用） |
| KnockBackDistance | 存储60，开关关闭 | 60，开关开启 |
| SuperDizzyDamage | 存储0，开关关闭 | 存储0，开关关闭 |

不能把这些值当最终伤害公式，也不能据此宣称这是所有普通敌人的统一参数。还需串起 AttackDB→HitBox 行→默认/覆盖→攻击者/防御者修正→实际应用路径；难度、技能、年龄、武器及状态修正是否适用，都应按该路径验证，不能预先假定。

`Structure` 暂按游戏自己的架势机制记录，不直接套用 LIAN 的“韧性/削韧”模型。`SuperDizzy` 暂保留原名，其积累、阈值、恢复和状态转换是独立待查主题。Hitstop 与受击控制时长也不能混称“硬直”。

### 另一个重要线索：Resilience / Resistance 与状态反应矩阵

除 Structure 外，本地 HitBox 行还有独立的 `m_bOverrideResilience` 和 `m_iOverrideResilienceValue`。部分敌人 DefenseComponent 明确引用 `UAttackPropertiesResistanceDB` 类资产（例如 Bodyguard、FireDisciple 和 Yang 的配置）。Resistance 资产中还读到 `m_ResistanceMatrix`、各 `m_Level`、自定义持续时长、使用受击动画时长、保留当前状态持续时长及阈值等开关/字段。

PDB 的 `FImpactResult::m_bResilienceImpact` 是 bool，不能误读成浮点“削韧值”。这些是韧性/受击反应研究的独立入口，值得与 Structure 分开追查；当前尚未证明其计算规则、优先级和对每种敌人的适用关系。相关原始属性另存 `exports/resilience-and-resistance-values.csv`。

## 4. 主角招式时序（已按用户要求加入）

已导出 300 行主角动画时序数据（含武器/特殊表），以及 255 个 AttackDB 对象；含 `_old` 路径的资产保留并显式标记，不保证所有资产实际使用。

- `m_iLastBuildupFrame` 与 `m_fHitFrame` 是动画表中实际读取的字段。
- AttackDB 还保存 `m_iWantedBuildupFrames`、动画帧率/时间间隔等。它们说明动画标注与目标节奏不是同一个字段，尚不能只拿 HitFrame/60 当实际前摇。
- 成功读取 314 条 HitBox 区间记录，以及 551 条 AvailabilityLayerWindow 记录，保留区间端点的类型、数值、层引用和命中条件。
- Open 区间的存储 Value 不是有效截止帧；AvailabilityLayerWindow 也不自动等于“可任意取消”。要继续解析对应 layer 的输入/动作许可及执行逻辑。

没有将内部行名自动翻译成玩家招式中文名，也没有把读取的区间包装成已实测的前摇/后摇/帧优势表。

## 6. 后续建议顺序

1. 优先深挖“倒地/起身 → Joker情境 → 哪些票据/数量/冷却变化”，把发现的状态绑定串成可解释的群体AI规则。
2. 串起一个普通敌人和一个主角招式的 AttackDB、HitBox行、Resilience/Resistance矩阵、受击结果与硬直结束条件，再扩展到批量参数比较。
3. 对照 Grunt Base/Advanced 的防御测试图与代码，验证攻击记忆、FirstParry tag、Structure/难度测试怎样影响决策。
4. 解析主角层许可和速度缩放后，再建立可靠的取消窗口与实战时序表。确需运行时验证时另行列明方法、对游戏/存档的影响，再决定如何做。

目前不需要用户安装工具或手动操作编辑器。下一轮可直接复用这里的清单和脚本；若要决定深挖分支，建议从第1项开始。
