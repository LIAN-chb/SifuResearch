# 研究续接与证据维护流程

本文件适用于机制研究、资产提取与解析、代码取证及研究成果维护。项目目标见 [PROJECT.md](../PROJECT.md)，任务入口见 [AGENTS.md](../AGENTS.md)。只读规则讨论按 [规则维护流程](rule-maintenance.md) 加载上下文；获准实施时登记治理批次。路径默认相对研究根目录。

## 1. 接手时只重建当前问题需要的上下文

用户指定的问题优先；用户明确要求继续研究但未指定问题时，从 [研究进度与问题](../Sifu/00索引/研究进度与问题.md) 的最新机制批次选一个可验收问题。提取与解析状态见 [解包与解析进度](../Sifu/00索引/解包与解析进度.md)，系统线索及证据术语按问题读取对应索引。

1. 从 [交接索引](handoffs/README.md) 找当前问题及相关进行中批次；核对最新研究进度及 [决策索引](../adr/README.md) 中适用决定。记录相互冲突时对照原始产物，按来源选定结论，日期和摘要只作线索。
2. 打开相关底稿的证据段、失败尝试和未解分支。对将要依赖的关键结论抽查原始资产字段或代码片段；扩展适用范围时核查新增条件。
3. 将本批真正检查过的材料及检查深度写入交接：只定位、读过摘要、核对字段／代码、重跑验证分别记录。阅读清单用于定位材料，机制是否已验证以证据段为准。
4. 建立唯一批次 ID，如 `20261028-服务条件-01`；使用 `notes/handoffs/<批次ID>.md` 并登记索引。确定一个问题、可检查的完成条件、写入范围及暂缓分支后开工。意外中断后，从最后持久化记录与实际文件恢复；缺失部分标为未知。
5. 开工检查 Git 状态和相关差异，按 [版本管理](version-control.md) 区分既有改动。按 [能力发现流程](capability-discovery.md) 核查当前工具、技能、插件和已有脚本／模板，再结合 [能力矩阵](tool-capabilities.md) 与 [方法复盘](retrospectives/README.md) 判断复用，必要时先做代表样本。

## 2. 先查现有产物，再决定执行

### 取证硬边界

- **全量提取需授权（停止型）**：默认定向提取目标资产、父级、默认对象及必要依赖；扩大到全量前说明必要性、范围和磁盘成本并取得授权，未获授权时停止扩大范围。
- **代码结论绑定构建（停止型，仅限该结论）**：代码取证前核对 EXE/PDB 匹配及哈希；不匹配时停止该构建结论，保留旧证据并分开记录。

以下是查找入口，覆盖范围与当前正确性以对应产物为准。先按资产路径、对象／字段、函数名、S／E 证据编号搜索相关记录，再打开必要内容。原始清单作为逐项记录，交接引用它们，不复制数千条资产台账。

| 要查的内容 | 现有入口 |
|---|---|
| 包内资源与初始提取范围 | `inventory/pak-list.txt`、`inventory/pak-overview.json`、`inventory/extraction-overview.json` |
| 初始提取文件及 SHA256 | `inventory/extracted-manifest.json`（路径相对 `extracted/`） |
| 初始解析能力与限制 | `inventory/package-parse-overview.json`、`inventory/deep-parse-overview.json` |
| 历史失败分类及定向重试 | `inventory/followup-gap-classification.json`、`inventory/followup-gap-reparsed-objects.json` |
| 补解包批次与定向资产 | `inventory/followup-unpacking-batch.json`、`inventory/followup-hitted-assets.json`、`inventory/followup-order-services-packages.json`、`inventory/followup-parry-ai-assets.json` |
| 代码取证、构建与输出哈希 | `inventory/*disassembly.json`、`inventory/pdb_overview.json`、相应 `logs/` 文件 |
| 配置覆盖边界 | `inventory/configuration-catalog-coverage.json`、`Sifu/03配置/覆盖范围与读表说明.md` |
| 历史检查结果 | `inventory/knowledge-vault-verification.json`、`inventory/followup-unpacking-verification.json`、`inventory/system-chain-evidence-verification.json` |
| 主题推理与机制关系 | `notes/` 对应底稿、`Sifu/00索引/系统线索与关系图.md`、对应实现篇 |

### 复用判断

| 情况 | 动作 |
|---|---|
| 输入构建／哈希、处理方式、产物完整性和所需覆盖范围均满足 | 直接复用并记录引用及本次核查范围 |
| 文件存在但没有可靠来源、版本或覆盖信息 | 标为来源／范围未核；先补核当前所需条目 |
| 只缺少依赖、对象或字段 | 定向补提取／补解析，保留原清单 |
| 输入或解析器变化、产物损坏、旧结果无法回答问题 | 记录重跑理由，使用独立批次输出，与旧结果比较 |
| 已知失败且输入、工具和方法均未变化 | 复用失败记录；出现明确重试条件后再试 |

同一资产可能在多个批次被不同解析器处理；按“输入哈希＋工具／脚本版本或哈希＋参数＋处理范围”区分结果。文件名相同和历史报告 passed 均只作线索。接手只核当前决策需要的证据；确需全量解包、全量重读或全量计算哈希时，先写必要性、范围与磁盘成本，登记批次后执行。

### 最小执行记录

每次提取、解析、代码取证或验证，记录工作目录、完整命令和参数、实际工具／解释器版本、脚本 SHA256、输入构建与相关清单、输出位置、退出码及限制。大量输入输出放批次 manifest，交接引用 manifest。命令包含敏感参数时脱敏并说明重新提供方式。

新增清单至少逐项标明源路径、源哈希、阶段、输出路径和成功／部分／失败状态；已有清单字段不足时由批次补充，汇总成功与条目失败分开记录。单项无哈希或版本不可考时写明未知，后续复核后再补。

## 3. 让结论可以被检查和修正

结论附可定位证据：资产路径＋对象／字段／行名，或函数名＋RVA＋构建标识。配置值只作输入证据。证据不足时写已确认部分，并单列“缺什么／影响哪条结论／下一步查什么”继续。推断写明依据、替代解释与可推翻它的证据，未解决冲突标为争议。

机制回答和文档按 [机制表达规范](mechanism-writing.md) 组织：先固定事件阶段和前提，说明确定规则与真实分支；未知项按输入、规则或观测缺口定位，其他阶段的因素仅在证据支持时引入。

每个关键结论在主题底稿有稳定定位：沿用现有 S／E 编号并注明所属文档，或增加命名锚点。记录问题、样本与构建、直接证据、推导步骤、成立条件、反证／替代解释及缺口。已有完整底稿只引用定位。

区分四阶段与三种表述：提取、解析、逻辑、实测分别记状态；直接观察、推断、未知分别陈述。静态路径接通之外，实际激活、完整时序和最终实战效果单独标注。

发现冲突时保留双方证据，先排查构建、继承／默认值、难度、状态、实例覆写与解析限制。旧结论被推翻后标为已修订／已撤回，说明原因并指向新结论；未改变的历史原始证据保留。用原术语、资源名和证据编号搜索所有受影响页面与生成脚本，记录修订传播完成或待修清单。历史备份保留历史身份，当前页面标明取代关系。

失败记录写明尝试对象、命令、错误或不支持范围、排除了什么、仍不能排除什么及何种变化值得重试。“没找到”“未解析”和“运行时不存在”按三种结论分别记录。

## 4. 控制写入和验证范围

开工在交接索引登记进行中批次和写入范围；该登记是人工协作提示，文件锁由实际写入前检查承担。同文件写入冲突先协调归属；无法协调时独立保存候选结果，归并前保持共享产物原样。旧批次是否结束以交接中的写入结束标记为准；无标记按“可能进行中”处理，先查实际文件再写。

**运行产物按批次隔离（停止型）**：新提取、解析、代码取证的运行产物默认写入 `exports/<批次ID>/` 或 `logs/<批次ID>/`；批次 manifest 可按已有工具约定带批次名写入 inventory/。执行前检查写入点，发现未登记的共享覆盖时停止该运行，先备份并登记范围。知识库、脚本、流程与交接等维护文件写回各自职责目录，归属见 [工作区目录约定](workspace-layout.md)。生成文档先查生成者及其输入；人工维护段与生成段明确归属。

验证按风险选择：文件存在／哈希、解析边界／引用、逻辑推导和运行时行为分层记录。验证报告应可定位到被检查产物、输入版本与检查器版本；缺少这些信息的旧报告仅作历史线索。相关输入或脚本变化后，受影响检查记为待重验；无关检查沿用旧报告。先保留旧报告，再运行会覆盖其输出的检查器。

### 只读检查

需要保持 `inventory/`、`exports/` 原样地复核时：

1. 将目标脚本复制到临时目录，例如 `%TEMP%/sifu-readonly/<批次>/`；原脚本与项目文件保持只读，改动只发生在临时副本。
2. 只把报告输出路径替换为临时路径；脚本用 `Path(__file__)` 推导根目录时，把根目录改为研究根目录。
3. 用 `python -B` 运行，避免写入 `scripts/__pycache__`。
4. 验收：项目内报告 mtime 不变，临时目录有报告，退出码原样记录。
5. 临时结果只作本次复核；需要长期保留时按正常流程写入批次目录并登记。

## 5. 收尾和中途交接

使用 [批次模板](handoffs/TEMPLATE.md)，每批只写变化和引用。批次可以完成一个问题，也可以因缺少证据而留下明确断点；问题未解决时保留未完成状态。规则维护批次注明不产生机制结论。

结束前核对：产物可定位；关键结论可追溯；失败和暂缓项已记录；适用检查有实际结果；修订影响已处理或列出；研究状态变化已同步进度与线索页；下一步指向具体对象／函数、输入和成功条件。中途及时保存断点，全部交接工作随进度分批写入。

权威记录按用途分工：机器事实在原始文件／manifest，推理和结论在主题底稿，当前问题与阶段在进度页，执行历史与断点在批次交接，用户决定与理由在 ADR。交接索引只导航和显示写入范围。证据记录冲突时按原始文件／manifest → 主题底稿 → 进度页 → 交接摘要回查来源；适用构建与范围核清后修正相应记录。

## 6. 用户决策及时落盘

识别到用户明确决定后，按 [ADR 约定](../adr/README.md) 主动记录，关联执行位置与本批交接；收尾检查本轮决定是否遗漏。候选建议标为“提议”，只有用户明确表态才转为“已接受”。方法经验注明适用假设、实际案例和失败边界，再逐步验证可复用范围。

## 7. 方法沉淀与版本收尾

遇到新工具能力或失败边界更新矩阵；有代表性的实际尝试按复盘模板沉淀，收益写实测值或标未知。验证后只提交本批文件，交接关联提交；规则变化同步知识库根目录的用户导览。本地版本历史与原始资产备份、运行时验证分开记录。
